# CAT Reference Data

Structured data extracted from the FINRA CAT specs in `docs/specs/`, meant to seed
the rules engine and RAG knowledge base. Generated by the scripts in `scripts/`
(each parses the relevant PDF with `pdftotext -layout`); re-run extraction
whenever the source specs are updated.

## `cat_error_codes.json`

Source: `docs/specs/06.26.26_CAT_Reporting_Technical_Specifications_for_Industry_Members_v4.2.0r1_CLEAN.pdf`,
Appendix E: Error Codes (v4.2.0r1).

365 records, one per CAT error/warning code. Fields:

- `code` — the numeric error code (string, as some are 3-digit e.g. warnings in E.4)
- `section` — spec subsection (`E.1` File Integrity, `E.2` Data Ingestion,
  `E.3` Linkage Discovery, `E.4` Warning Error Codes)
- `section_name` — human-readable section title
- `severity` — `"Error"`, `"Warning"`, or `null` for a handful of `Reserved`
  placeholder codes with no description
- `text` — description + explanation columns concatenated (the source table's
  two text columns were merged during extraction rather than kept separate,
  since the PDF's line-wrapping made splitting them unreliable)

Known limitation: description and explanation are merged into one `text`
field rather than kept as separate columns — good enough for RAG grounding
and for surfacing "what does error 2019 mean" to a user, but if the rules
engine later needs the short description alone (e.g. for a summary table),
that will need re-extraction with a more careful column split.

Generated by `scripts/extract_cat_error_codes.py`.

## `cat_data_dictionary.json`

Source: same PDF, Appendix G: Data Dictionary (v4.2.0r1).

132 records, one per CAT event field. Fields:

- `field` — the field name as used in CAT submissions (e.g. `accountHolderType`)
- `data_type` — one of the data types defined in Table 3 of the spec
  (`Choice`, `Boolean`, `Text (64)`, `Timestamp`, `Price`, `Whole Quantity`,
  `Aggregated Orders`, etc.), including the size annotation where the spec
  gives one (e.g. `Text (64)`, `Numeric (6,4)`)
- `description` — the field's description, including its "Allowed Values"
  list where the spec provides one (for `Choice` fields) — kept as running
  text rather than parsed into a separate values list
- `data_type_inferred` — present and `true` on 19 fields (e.g.
  `aggregatedOrders`, `senderIMID`, `handlingInstructions`) whose data type
  name wraps across a PDF line break in a way the parser can't recover from
  text order alone; these were filled in via a manual override table in the
  extraction script (`TYPE_OVERRIDES`), cross-checked against Table 3 and
  the field's own description. Re-verify these against the spec before
  relying on them for anything more than the RAG knowledge base.

Known limitation: `description` is not parsed into separate value-code /
value-meaning pairs for `Choice` fields, so the validator will need its own
allowed-values lookup (or a further extraction pass) to check that e.g.
`accountHolderType` is one of `A/E/F/I/O/V/P/X` — right now that's only
available as prose text for RAG, not as a checkable list.

Generated by `scripts/extract_cat_data_dictionary.py`.
